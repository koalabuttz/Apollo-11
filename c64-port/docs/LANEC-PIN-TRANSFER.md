# PINBALL_GAME_BUTTONS_AND_LIGHTS on the transfer ABI

Lane C. Milestone `lanec-pin-transfer`.

## What it adds

Pinball's native code is spread over many earlier modules (the `dsky_*`,
`cm_*` and `lanec_pin_gaps` translations), each run by one `pw-*` suite of
the Lane C harness (`lanec-pw`) or by `pin-gaps`. This milestone registers
every point at which those suites enter a module as a routine of the
transfer ABI (`docs/NATIVE_TRANSFER_ABI.md`), so the flight program can
reach Pinball through BANKCALL, POSTJUMP and plain TCs.

- `src/lanec_pin_routines.inc` (generated by `tools/lanec/routines.py pin`)
  holds the sorted tables: 267 Luminary099 routines in
  `lanec_pin_lm_routines` and 262 Comanche055 routines in
  `lanec_pin_cm_routines`. The earlier modules overlap, so each routine
  lists the modules that claim its point; it tries them in order on the
  state as it came in and keeps the first that accepts.
- `src/lanec_pin_routines.c` wraps the modules. io is the mission's
  downtelemetry device record, as for EXTENDED_VERBS (`lm_dntm_io`, with
  channel 11 from `program->hardware`; `cm_dntm_io`). A module that writes a
  channel the record does not carry (CHANLOAD's `WRITE` to any channel) is
  refused.
- Pinball returns through erasable words: `TC Q`, `TC L`, and the cells in
  `lanec_pin_cells` (RUPTREG3, DSEXIT, WDRET, UPDATRET, SFTEMP2, MIXTEMP,
  ENTRET, DSPWDRET, MPAC, MPAC +2, MPAC +6, REQRET and 0116). When a module
  ends at a register or one of these cells and it holds a TC (not RELINT,
  INHINT or EXTEND, and not to itself) or a TCF into fixed memory, the
  routine executes that one instruction, so the next routine starts where
  the original goes.
- The return point after each of the file's BANKCALL/IBNKCALL sites (the
  CADR + 1) is registered through SWRETURN: the earlier modules enter there
  only at SWRETURN, so the routine gives the state back to SWRETURN (BUF2 =
  the point, BUF2 + 1 = its bank, FB = the bank SWRETURN restored), which
  then rebuilds exactly this state, and runs the modules that claim SWRETURN.
- Luminary's SWRETURN and ISWRETRN (`src/lm_interbank.c`) no longer require
  Q to be a caller address: a BANKCALLed routine reaches them by `TC Q`,
  which leaves Q = 3.

`routines.py pin --check` (run by `make test-lanec-pin-transfer`) fails
unless, in both missions, every label of the file is registered except the
internal subroutines it lists, and every return after a TC to a label
outside the file is registered (15 each).

## Round trips

`tests/lanec_pin_transfer_cases.c` (suite `pin-transfer`, 2,048 cases) has
two kinds of case:

- the genuine callers outside the file whose BANKCALL or POSTJUMP CADR names
  a Pinball routine (8 cases);
- every registered routine from its own entry, with up to four accepted
  cases of the first module it tries (2,040 cases), chained through the
  routines that follow it.

Channels the device records do not carry are 0. `agc_transfer_run` runs
INTER-BANK, the display interface and the Pinball tables, and for
Luminary099 the Executive's job services. The oracle runs the unchanged
original program in Virtual AGC over the file's words, the code of other
files the modules run inline (taken from the oracle traces of all `pw-*`
suites: SHORTMP, JOBWAKE, ...), the return cells and BUF2 while they hold a
transfer (`LANEC_TC_CELL`), INTER-BANK, the display interface and the
Executive, and stops at services that hand control away for good (ENDOFJOB,
JOBSLEEP, TASKOVER, POODOO, BAILOUT, CCSHOLE, CURTAINS; Luminary also at the
Executive's idle loop ADVAN).

A case passes when the native chain ends at an unmapped continuation and
the complete state matches the oracle there. A chain is refused, with the
state restored, when it ends where the oracle would go on (a point inside
those words that no routine claims, reached through a random return address
or cell) or when a routine refuses its state midway: the entry chains start
from module cases whose return cells and Q hold random values, so many
leave the modules' domains after the first routine. 1,212 cases are
identical to the original and 836 are refused unchanged, in strict and
ASan/UBSan builds.

`pin-transfer-c64` (32 Luminary099 cases) runs the decimal display's entry
chains (DSPDECWD, DSPDECNR, 16 cases each) with only INTER-BANK and the
decimal display's routines registered (`lanec_pin_lm_c64`), against the
oracle with the same boundaries less the Executive's services: 28 are
identical and 4 refused; `make vice-lanec-pin-transfer` runs all 32 on a
VICE PAL C64.

## Harness changes

- `LANEC_TC_CELL` (`include/lanec.h`): a range bank for erasable words the
  original executes only while they hold a TC or TCF transfer.
- `tools/lanec/oracle.c`: a case that finds no boundary within 1,000,000
  instructions prints status 3 (it never matches a native row);
  `LANEC_STEPS=N` prints case N's instructions to stderr.
- `build/lanec-native --exits SUITE` prints each accepted case's exit after
  its entry, for `routines.py pin`.

# Comanche055: bootable C64 application

Generated by `tools/boot_acceptance.py cm` at commit `d7abace4fc66`. Result: **PASS**.

This is the `bootable_c64_application` evidence of the `integrated_applications.Comanche055` entry (docs/PORT_SCOPE.md). It shows the whole program booting on a stock C64 from its disk images alone, with nothing else prepared on a PC: the loader fills a 2 MB REU from the disks, the flight resident verifies the store and starts the AGC with the hardware restart (GOJAM), and the crew's keys then select P00 on the DSKY on the C64 screen.

Every run below is in VICE (x64sc, PAL, stock 1 MHz C64, 2 MB REU, the Commodore KERNAL, BASIC and character ROMs), with true drive emulation except in the `1581-kernal` run, where VICE's virtual drive serves the KERNAL's reads. Each one types RSET, `V37` ENTR `00` ENTR after the boot and passes only when the AGC is in P00: MODREG 00000 and `00` under PROG on the screen. Speed and real time are not acceptance criteria (docs/PORT_SCOPE.md); the times are given to say what to expect. Users' steps: docs/RUN-ON-C64.md.

Load is the loader reading and expanding the disks into the REU (from its own CIA count, PAL cycles); the store check is the flight resident verifying every module header and CRC, the resolver and the rope's site words before the GOJAM. The KERNAL's own load of the 6 KB loader adds about 10 s. A disk asked for twice means the loader did not take the first try: the run attaches the next image and presses RETURN at once, as a person might. The KERNAL loader (the 1541 and 1581-kernal runs) reads the drive's status after opening the disk's id file; while a 1541 that has not yet seen the new disk reports 74 DRIVE NOT READY it waits a second and opens it again, up to five times (#1012, #1015). On any other error, or an id that is not the new disk's, the loader asks for the disk again, as it would on real hardware. The loader's message at each ask is in the run's JSON (`swap_prompts`). Boot status 0 means every store check passed. Each boot record (`cm-<run>-boot.json`, written by `flight_disk.py --p00`) binds the commit, the disk images, the loader and resident PRGs, the REU store image and the VICE log by SHA-256.

REU bounds is the check of acceptance item 9 (tools/reu_layout.py, #681) on each boot. The loader first checks for a 2 MB REU (one byte at the start of each 64 KB bank) and clears all of it. From then on VICE traces every REU DMA, read or write: the disks' data, the hand-off's fetch of the resident and the AGC's run, and logs any whose range is not inside the program's declared layout plus the resident's stage at the top of the REU (`<run>-monitor.log`; tools/flight_disk.py boot_layout). VICE now and then evaluates a DMA's condition only after it ran; then only its last byte is range-checked (the count is in the table, #681's limit as in the flight runs), and its writes are still covered by the byte check: after the run, every REU byte that differs from the store image must lie in a writable region. A run passes only with both clean, the trace's three checkpoints set as VICE numbered them and at least one DMA seen, which this tool checks again from the monitor log. The run's JSON lists the regions it checked against.

## Keyboard

In the `1581-keyboard` run the keys are pressed on VICE's window through the X server (XTEST), so they reach the AGC the way a user's do: the C64's keyboard scan reads the CIA matrix 25 times a second and queues each DSKY key, and the AGC takes it at its next idle as a KEYRUPT. RSET, `V37` ENTR `00` ENTR reached P00: yes. The key map (docs/RUN-ON-C64.md, The DSKY): `0`-`9`, `+`, `-`, `V` VERB, `N` NOUN, RETURN ENTR, `C` or DEL CLR, `R` RSET, `K` KEY REL, `P` PRO.

## In CI

Every port-ci run whose changes touch a file on the watch list in tools/mk/ci-extra.mk (`ci-watch-flight-disk-vice`: the disk tool, the loader, the drive code, the decompressor, the resident's main, the REU store code and the REU layout check) runs `make flight-disk-vice`: the `1581` run above for both programs, and the check disk. It fails unless both reach P00, the boots stay inside the REU layout and the check passes. A change outside the list (the store's modules, the rest of the resident) does not re-run it, so a program's flip PR regenerates this doc at its own commit (tools/boot_acceptance.py). The run keeps the boot records (`flight-disk-boot-<m>.json`), their VICE logs and the disk images it booted in its `c64…-logs` artifact.

## Hardware check disk (the LM build's)

There is one check disk, and it is built from the LM's store: it checks the machine (the C64, its REU and its drive) rather than one program, so it runs LM code, not Comanche055. It is reported here because a C64 that fails it is not fit to run either program. This program's own boot is the runs above.

The check disk (`test-1.d81`, `LOAD"APOLLO TEST",8`) loads the LM's store like the LM disk, then measures the video standard, the REU's size and DMA speed, runs the LM's P63 for 200 cs from a host snapshot with the host's inputs, and compares a CRC of the end state against the one VICE gave when the disk was made (docs/RUN-ON-C64.md, Check on real hardware).

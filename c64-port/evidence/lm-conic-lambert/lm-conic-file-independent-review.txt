Conclusion: The record holds up. Every cited file exists, its bytes match both the record and the milestone's SHA256.json, and each xz archive decodes to the recorded decoded_sha256 (269090816 bytes = 65536 x 2053 words). The word counts add up to 1072 and match the whole-file line. On the native side, all three rare branches are taken by all 32 of their bucket entries and by no other entry. Findings
- (1) Citations. For each milestone the record cites 5 files: source-stream.json, reference.snapshots.bin.xz, checks.log, results.json and source-map.json. All 20 exist, and each sha256 equals the record value and the SHA256.json value. Every manifest entry matches the bytes on disk, including lm-conic-file-record.json and lm-conic-file-checks.log in the lambert manifest. For each milestone, the decoded_sha256 in source-stream.json equals the one in the record and equals the sha256 of the decompressed xz. The vice lines equal results.json c64.results. lm-conic-file-checks.log is exactly the four checks logs, each under its "== id (scope)" header.
- (2) Words. Record: 338 + 265 + 123 + 346 = 1072. Whole-file line (lambert checks log line 5): CONICS1 constants 29 + kepler 338 + lambert 316 + timerad 123 + timethet 265 + "lm-conic-timethet (ltt_havenorm)" 1 = 1072. Lambert's 346 is 316+1+29, so the record counts the HAVENORM RVQ word, which the whole-file line assigns to timethet, under lambert. The scope label says so. The total is unaffected. Note that tools/lm_conic_file_record.py hard-codes these counts and does not read them from the log. The per-milestone source maps report 290 words for timethet, which includes words shared with LAMENTER/NEWSTATE; the record uses the 265 owned words.
- (3) Logs. The oracle PASS line "PASS65536 original ... oracle entries equal native 2053-word rows <hash>" is present for timethet (ad121738...b25acf) and lambert (b312345d...ea06d3), and both hashes equal decoded_sha256. Kepler and timerad have no such line, because they were not rerun. Their logs do have "PASS all retained source-state bytes: 269090816 SHA256 <hash>", which equals decoded_sha256 (501521398e...20e0 and 6207be44...f266). All four logs have PASS lines for strict native and full ASAN/UBSAN over 65536 entries. Cosmetic: "PASS65536" has no space.
- (4a) POLYCOEF BMN INFINITY (AGC 1242-1243; src/lm_conic_timethet.c:260). My instrumented copy over all 65536 timethet entries gives 32 hits: 32 of 32 in bucket 1333 and none outside it. Statuses are 50122 returned and 15414 at ABTCONIC, the same as the stream. At the hits, R1A = 77677 77777 (-1024^2 lsb) or 76777 70136 (-2897^2 lsb). MPAC after BDDV is 57777 77777 (-0.5, so W = -2^-6 = -1024*2^-16). This matches the doc. The doc's reachability argument holds: GETX sets X2 = 3 with S2 = 1, so there are three passes, and any pass that leaves W < 0 with a nonzero root is caught by the next pass's BMN. One algebra slip: the doc says the new W^2 + R1A/16 equals "2 sqrt(D) W". It actually equals 2D + 2W sqrt(D) = 2 sqrt(D)(sqrt(D) + W), where D = W^2 + R1A/16. It is still < 0 because R1A < 0 gives sqrt(D) < |W|, so the conclusion stands.
- (4b) DSU BMN COGUPLIM falling through to UPLIM (AGC 1411-1414; lambert.c:163-165). Over all 65536 entries: 32 fall-throughs, all in bucket 1717 (32 of 32), with no BOV in that bucket and status 1 for all of them. Elsewhere, 9702 entries go BOV->UPLIM and 47443 go DSU BMN->MAXCOGA. The doc's condition, COGAMAX in [COGUPLIM, 1) with no overflow, is right. An exactly-zero difference also falls through.
- (4c) BZE NEGP (AGC 1449-1451; lambert.c:223). Over all entries: 32 BZE hits, all in bucket 717 (32 of 32). Bucket 717 has no BMN NEGP hits, and 11072 other entries take BMN NEGP. Overall statuses are 60534/5002, as in the stream.
  DISCREPANCY (docs and the cases comment, not code): the explanation does not match these cases. The docs (LM-CONIC-LAMBERT.md "Rare source paths") and the comment at tests/lm_conic_lambert_cases.c:114-118 say a tiny nonzero 1-CSTH passes ROUND BZE 360LAMB and the DDV quotient then truncates to zero. In all 32 cases, CSTH is computed one lsb above 0.5 (20000 00001). SR1 BDSU D1/4 then leaves MPAC = 77777 77777 20000, and STORE writes 1-CSTH as DP negative zero (77777 77777). ROUND carries the positive half-lsb third word, so MPAC becomes 77777 00001, which is nonzero, and BZE 360LAMB is not taken. LAMBLOOP then reloads the stored -0 1-CSTH, the quotient is zero and BZE takes NEGP. So the branch is reached because ROUND/BZE tests the rounded TP MPAC while the stored DP value is zero, not because a nonzero 1-CSTH truncates. The doc's mechanism may be possible in principle but none of the 65536 entries uses it. The "about 2^-19" threshold is likewise not what the cases show. The oracle comparison covers these entries either way.

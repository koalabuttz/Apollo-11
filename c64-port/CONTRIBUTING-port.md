# Working on the native C64 port

One page for lane threads and people. The verification bar is
[docs/PORT_SCOPE.md](docs/PORT_SCOPE.md); this page is the workflow.

## Branches

- `port/c64-native-c` is the integration branch. Nobody pushes to it directly.
- Each lane works on `port/<lane>/<topic>` (for example `port/a/waitlist-restart`)
  and opens a PR into `port/c64-native-c`. A PR merges only with green `port-ci`.
  If the base has moved since that green run, merge the base into your branch
  and wait for CI again before merging: two PRs that are each green alone can
  still break the base together (a shared struct gains a field, another lane's
  new test still uses the old initializer).
- `port/pipeline/*` is for shared tooling (the Pipeline thread, then the steward).
  Only those branches may change the shared files listed below.

## Get a working tree fast

A full clone downloads 16 GB of legacy evidence. Skip it:

```sh
git init Apollo-11 && cd Apollo-11
git remote add origin https://github.com/koalabuttz/Apollo-11
git fetch --filter=blob:limit=1m --depth=1 origin port/c64-native-c
git show FETCH_HEAD:c64-port/tools/ci_checkout.sh | bash -s FETCH_HEAD
cd c64-port && tools/setup_cloud.sh && source deps/env.sh
```

That takes about two minutes. `setup_cloud.sh` installs the pinned LLVM-MOS
SDK, VICE `x64sc` with hash-checked C64 ROMs, and the Virtual AGC reference
fixture under `deps/`. Build with `SKIP_EVIDENCE_RESTORE=1` in a lean tree
(export it). `tools/ci_run.py TARGET...` runs targets and fetches any skipped
legacy evidence a test turns out to need.

## Start a milestone

```sh
python3 tools/new_milestone.py lm-servicer-avetoms --lane F \
    --title "Translate Luminary SERVICER average-g integration"
```

It creates everything a milestone owns, and nothing shared:

| File | Purpose |
|---|---|
| `docs/milestones/<id>.md` | Index entry: title, date, lane and a one-paragraph summary ending in `See docs/<ID>.md.` |
| `docs/<ID>.md` | Long-form record: scope, source map, evidence |
| `src/`, `include/`, `tests/`, `platform/c64/` | Module, host test and C64 diagnostic |
| `tools/mk/<id>.mk` | `test-<id>`, `sanitize-<id>`, `c64-<id>`, `vice-<id>`; hooks into `all`/`test`/`sanitize` |
| `evidence/<id>/SHA256.json` | Evidence manifest |

The Makefile picks up `tools/mk/*.mk` automatically. Keep targets named
`test-<id>`, `sanitize-<id>`, `c64-<id>` and `vice-<id>`: CI selects them by name.
A C64 diagnostic reports through the `$c000` mailbox that `tools/vice_run.py`
checks: write the failure count to `$c001-2` and the check count to `$c003-4`,
then `$a5` to `$c000` last.

Don't hand-translate a file that has interpretive code. Generate it with
`tools/interp_compile.py`: add a spec to `tools/interp_specs.py`, and the
compiler writes `src/<base>.c` and `include/<base>.h` from the yaYUL listing as
transfer-ABI routines. It handles the basic code between EXIT and TC INTPRET
too. See `docs/INTERP-COMPILE.md`. Lanes that have used it report a file
taking about an hour instead of about a day. If the compiler lacks an order
or an instruction form, add it to the compiler and keep the generated files
byte-identical for every existing spec (`interp_compile.py --check <spec>`).

## Formatting

Write readable C, even where it reads like assembly: one statement per line,
octal rope words as written. Run `make hooks` once per container (or `make
format`, which also installs it): the pre-commit hook formats the lines each
commit touches with the pinned clang-format and `.clang-format`. It never
reflows untouched lines, because cover records key branches by file:line.
Generated files ("Generated by ... do not edit") are left to their generator.
CI's `format` job warns about changed lines left unformatted. Formatting
changes no compiled byte.

## Never edit these by hand

CI rejects a lane PR that touches them:

- `README.md`, `docs/HANDOFF.md`, `docs/ROADMAP.md`, `docs/VERIFICATION.md`,
  `docs/SOURCE_MAP.md`. They are generated by `tools/ledgers.py` from
  `docs/ledgers/` (frozen pre-split text) and `docs/milestones/`, and rebuilt
  automatically after each merge. Your milestone file is your ledger entry.
- `Makefile` (frozen; add `tools/mk/<id>.mk`).
- `evidence/SHA256.json` and any file directly under `evidence/` (legacy).
- `docs/milestones/legacy-*` and `docs/ledgers/*`.

`docs/port-coverage.json` stays shared: change only your own files' entries.

## Evidence

New evidence lives in GitHub releases, with hashes in git:

```sh
python3 tools/evidence.py add <id> build/foo-native.snapshots.gz build/foo-vice.log
python3 tools/evidence.py add <id> --tree build/foo-proof.json   # small text kept in git (<= 256 KiB)
python3 tools/evidence.py push <id>        # uploads via the evidence-upload workflow
python3 tools/evidence.py verify <id> --remote
```

`push` sends the bytes on a throwaway `evidence-upload/<id>` branch; the
workflow publishes them as assets of release `evidence-<id>`, checks every
hash and deletes the branch. Commit only `evidence/<id>/SHA256.json`,
`evidence/<id>/.gitignore` and `--tree` files. Anyone can restore the bytes with
`tools/evidence.py fetch <id>`. Coverage certificates may cite
`evidence/<id>/<file>`; CI fetches cited release files before the audit.

## What CI runs

`port-ci` on every PR into `port/**` and push to `port/**`:

- shared-ledger guard, milestone files render, and published evidence for the
  milestones a PR touches;
- `tools/port_coverage.py` (the inventory and immutable-source audit);
- host and sanitizer targets the change can affect (`tools/ci_affected.py`,
  following `#include "..."` from each target's sources), or the whole suite
  when shared plumbing changes;
- LLVM-MOS builds and VICE `vice-<id>` runs for affected C64 targets, plus the
  base Executive VICE check.

The full suite runs nightly against `port/c64-native-c`, and on demand from
the Actions tab (`port-ci`, Run workflow). Those requested full runs (not a PR
that touches shared plumbing) also run every legacy
`tools/*_vice_test.py` script, split over eight `c64-legacy` shards, as the
`vice-legacy-<name>` targets that `tools/legacy_vice.py` writes to
`tools/mk/legacy-vice.mk`; run one locally with `tools/ci_run.py vice-legacy-<name>`.
A script your milestone records as an unqualified development trial (never
passed, replaced by a staged script) goes in `TRIALS` in `tools/legacy_vice.py`
with the document that says so; anything else that fails is a failure to fix.

## After acceptance

Both programs are accepted (docs/acceptance/). Their bootable docs record the sha256 of the
REU store, resident, loader and disks each program ships. `tools/acceptance_freshness.py`
(after `make flight-disk`) compares those with the build and prints FRESH or STALE per program.

port-ci's `acceptance-fresh` job runs it with `--require-fresh` on every PR that touches C64
code. A PR that moves an accepted program's bytes fails there unless it also re-cites that
program's acceptance at its head (the regenerated docs/acceptance/<program>-*.md). In practice:

- Get green CI elsewhere and a reviewer accept, then tell the steward the PR is READY and which
  program it moves. The steward merges waiting PRs for that program into one re-acceptance
  window PR, runs the program's acceptance at its head and commits the docs there.
- A fix for a failing acceptance check ships with its own re-run.
- Tools, host-only and docs PRs, and PRs that leave both programs FRESH, are unaffected.

`docs/acceptance/pending-reacceptance.json` names a program the base already knows is stale, the
PR that made it so, and the sha256 of each file that moved then. That program reports STALE without
failing only while those files keep their pinned hashes (any further move fails), until its
re-acceptance PR deletes the entry. Adding an entry is a reviewed change, never a way around the check.

## Pick the C64 rows by outcome

The C64 runs a subset of the host cases. Pick it with `tools/c64_row_cover.py`,
not by stride or fewest edits: it builds a host runner with `--coverage`, runs
it one case at a time and reads every branch arc each case takes in every
linked source (`gcov -b -j`). `cover()` returns the fewest cases whose arcs
equal what the whole host corpus takes; `check()` fails, listing each missed
arc as `file:line branch N`, when a row list falls short.

```sh
python3 tools/c64_row_cover.py pick --objdir build/foo-cover --cases 512 --budget 96 \
    --trace build/foo-arcs.json -- build/foo-cover/runner {case}
python3 tools/c64_row_cover.py check --objdir build/foo-cover --cases 512 \
    --rows 0,17,40 --trace build/foo-arcs.json
```

The runner takes the case number as its argument (`tools/lane_f_path_trace.c`
does). From Python, `host_trace(objdir, sources, flags, cases)` builds and
traces in one call, and `summary()` gives the proof fields. Interpreter-routine
specs opt in with `'c64_rows': 'cover'` in `tools/interp_specs.py`; specs
without the key freeze byte-identical vectors.

Generators should also reach flight-typical values a seeded fill misses: +-0
high words, equal times, zero and full-scale vectors, and non-zero TIME1,
TIME2 and CDU cells (`tests/interp_case.c` clears 010-061 before the case's
edits, so only edits set them). `tools/edge_cases.py` returns these as
`(address, word)` edits; interpreter-routine specs opt in with
`'edge_cases': True`, which adds them as a fourth case shape.

## Done means the PORT_SCOPE certificate

A file flips to `complete` in `docs/port-coverage.json` only with all four
evidence categories (source-to-native map, independent assembly comparison,
host and sanitizer results, C64 execution results) and after the auditor's
review. The independent assembly comparison and the two results categories
must each be their own record (a comparison, a host run, a C64 run), never the
source-to-native map cited again: `port_coverage.py` rejects such a complete
certificate, and `ci_guard.py` rejects a drafted or complete certificate a PR
adds or edits that does. Every entry the file's code is reached at from another
bank (BANKCALL, IBNKCALL, POSTJUMP and the like) must be registered as an
`agc_transfer` routine, or the auditor sends the certificate back. Interfaces have owners: Lane A owns the interpreter and executive ABI,
Lane H owns the overlay and module ABI; change them through a PR the owner
reviews.

Before you draft a certificate, run `python3 tools/cert_precheck.py
<AGC file> --fetch` (or `--changed --base origin/port/c64-native-c`). It
checks the rejection patterns from past audits: distinct, real evidence
records (no map cited twice, sha256 matching); a comparison that is a
yaAGC/oracle run with a case count above zero and no differing cases; results
that show a pass (C64 results from VICE); no open items in the scope text; every
entry reached from another file and every interpretive resume word (CHANG2)
registered in `agc_routine_entry`; refusals, with NEWJOB refusals flagged; and
the C64 row cover through `tools/c64_row_cover.py` when the record names its
rows. Each finding is a FAIL or WARN line with a fix hint. `ci_guard.py` runs
it on every certificate a PR changes and fails on any FAIL. WARN lines are
things it cannot settle mechanically (edge and signed-zero paths left
uncompared, whether domain claims hold, C64 cover without a runner): argue
them in the certificate. A clean precheck does not mean the auditor will
accept it. If you change how routines are reached, regenerate its listing facts
after `tools/setup_cloud.sh` with `python3 tools/cert_precheck.py --write-facts`.

A certificate names the VICE targets that prove its C64 run, in
`evidence.c64_execution_results.vice_targets`, as `{"vice-<m>": <checks>}`
(the check count it certifies; a plain list of names certifies a pass), or
says why none applies in a certificate-level `"c64_exempt": "<reason>"`
(documentation-only files). Each full `port-ci` run (nightly, dispatch)
uploads a `vice-manifest` artifact (`tools/vice_manifest.py`): for every
`vice-*` target, its result, check count, failures and PRG sha256 at that
commit. `cert_precheck.py` (with `--fetch`, or `--manifest PATH`) fails when a
named target is missing, failed or ran fewer checks in the newest complete
manifest, or when that manifest is over three days old; it only warns while
the manifest predates the certificate's `vice_targets`, when no manifest can be
fetched, and, during migration, for certificates that name no targets. The
manifest is what proves the C64 run at the tip, so after a shared-file change
you need not refresh the PRG hashes in older run records.
